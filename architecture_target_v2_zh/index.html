    MayaTool 目标架构 v2¶

    last_verified_commit: 38431cfe last_verified_date: 2026-09-06 status: target-architecture

    本文档定义 MayaTool 下一阶段的目标架构。它服务于两个产品表面：Maya 工具盒和 AI 助手。工具盒、AI、MCP、快捷键和工作流不是五套执行系统，而是同一套能力运行时的不同入口。

    1. 产品内核¶

    平台长期只保留三个一等业务对象：

    1. Capability：可执行能力。任何会修改 Maya 场景、文件或外部状态的动作，都必须有稳定 ID、版本、action、参数 schema 和治理策略。
    2. Shortcut：能力的访问入口。Quick Panel、收藏、钉选、快捷键和 Marking Menu 都是入口投影，不是另一种执行类型。
    3. Workflow：多个 capability action 的有序组合，包含依赖、参数绑定、版本和执行策略。

    “普通工具”和“标准能力”不再作为两套正式执行模型。旧的普通工具只有三种结局：迁移为 Capability、明确归档、直接删除。不会为已决定淘汰的接口保留长期兼容层。

    2. 唯一执行链¶

    Maya UI / AI / MCP / Hotkey / Marking Menu
                  |
                  v
         Application UseCase
                  |
                  v
        Plan / Contract Validation
                  |
                  v
          ExecutionGateway
                  |
                  v
       Maya Adapter / File Adapter
                  |
                  v
       Structured Result + Receipt

    ExecutionGateway 是所有正式副作用的唯一 authority。入口只选择 capability 和 action，不得决定是否绕过治理。contract 缺失、action 不存在、能力等级无法确认或策略校验失败时，执行必须失败并返回结构化 error_code。

    FlowRunner 只负责多步骤依赖、顺序和上下文传递；它不重新实现授权、contract 校验或 Maya 副作用。AI 只负责理解、计划和解释，不能直接调用工具 callback。

    3. 五层边界¶

    presentation
    Maya 面板、快捷入口、状态展示、MCP adapter

application
    用例、查询服务、工作流编排、能力生命周期

domain
    Capability、Workflow、策略、不变量和状态转换

runtime
    Registry、Contract Validator、ExecutionGateway、FlowRunner

infrastructure
    Maya、文件系统、配置、日志、provider、repository

    依赖规则：

    • Domain 不依赖 Qt、Maya、文件系统、翻译文本或具体 UI。
    • UI 只调用 Application 用例和查询服务，不直接写 Repository、ToolManager 或 CategoryManager。
    • Application 不依赖具体 Widget。
    • Infrastructure 不反向依赖具体 UI。
    • core/ 只作为待删除的历史兼容区，不再承载新业务规则。
    • AI、MCP 和外部编辑器只能是 adapter 或 planner，不拥有第二份 registry、授权或 receipt。

    4. 目标目录¶

    floating_toolbox/
  product/
    capabilities/       # Capability descriptor, registry ports, lifecycle
    workflows/          # Workflow definition and application usecases
    toolbox/             # Catalog query and shortcut projections
  runtime/
    execution/          # Request, result, policy, gateway, flow runtime
  application/
    usecases/            # Commands and queries
  domain/
    capability.py
    workflow.py
    policies.py
  infrastructure/
    maya/
    persistence/
    providers/
    projections/
  presentation/
    panels/
    dialogs/
    adapters/
  authoring/
    package_templates/
    contract_generation/
    file_edit/
    verification/

    ai/ 保留为规划和对话实现，但不得成为执行层。rig_intelligence/、研究型探针和实验代码默认移出产品核心启动路径；没有正式消费者的模块不应继续通过“以后可能使用”留在运行时。

    5. 能力包唯一格式¶

    正式 Capability 必须包含：

    tool_manifest.json
tool_contract.json
governance.json
tool.py
cards/                 # 可选的示例 Workflow
tests/                 # 能力自身的最小验收

    tool_manifest.json 只负责身份和加载入口；tool_contract.json 是 action 与参数协议真相源；governance.json 是风险和执行策略真相源。没有 contract 的脚本可以作为外部脚本存在，但不得进入 AI 工具面、Workflow 或正式 Capability Registry。

    6. 硬切规则¶

    • 新路径落地后，旧路径在同一批次删除代码、测试和文档引用。
    • 不增加 *_compat_service、旧入口 wrapper 或长期 fallback 来延长淘汰接口寿命。
    • 删除前必须证明生产消费者已经迁移；只被测试或旧文档引用的代码不构成保留理由。
    • 允许降级的地方必须记录结构化事件；不能以 except: pass 或空值伪装成功。
    • 每个重构切片都必须通过 Python 测试、compileall 和 Maya 2026 入口级验证。

    7. 完成定义¶

    目标架构完成的最低条件：

    • 正式 Capability 的执行 authority 只有一个。
    • UI、AI、MCP、快捷键和 Workflow 共享同一套 request/result 语义。
    • Domain 无 Qt、Maya 和文件系统依赖。
    • UI 无直接 Repository 写路径。
    • 正式能力全部有 manifest、contract 和 governance。
    • 旧 Manager、旧 callback 执行路径和兼容服务已从生产路径删除。
    • 工具盒四类面板、AI 单 action、Workflow 多步骤和关闭清理均有 Maya 2026 验收证据。
